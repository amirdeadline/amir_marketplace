## 1. Introduction

### 1.1 Purpose

This document specifies what amir_md must do and how well it must do it. It turns the product requirements in the PRD into testable software requirements for the first release, a VS Code extension, and sets the constraints that keep the second release, a Windows desktop app, possible without a rewrite.

### 1.2 Scope

amir_md is a word-processor style editor for Markdown files. It shows a Markdown file as formatted text, lets the user edit it with a Word-like toolbar, shows the document's headings in a navigation pane, folds sections under their headings, and exports to PDF and Word. The file on disk stays Markdown, and content the user did not edit keeps its exact original text.

In scope for release 1: the VS Code extension, with Windows as the primary platform. Out of scope for release 1: the Windows desktop app (release 2), real-time collaboration, track changes, comments, Word or PDF import, and special rendering of project-specific syntax.

### 1.3 Definitions

| Term | Meaning |
|---|---|
| Block | A top-level Markdown element: paragraph, heading, list, table, code block, block quote, thematic break, HTML block, or source block. |
| Source block | A block amir_md keeps as raw Markdown because it cannot show it as formatted text. |
| Block source map | The start and end offset of each block in the document text, taken from the last parse. |
| Splice | Replacing only the text range of a changed block, leaving the rest of the file untouched. |
| Fold | Hiding the content under a heading in the editor view. It never changes the file. |
| Fold range | The blocks a fold hides. |
| Entry | One heading as shown in the navigation pane tree. |
| Host | The program that runs the editor UI: the VS Code extension in release 1, the desktop shell in release 2. |
| Host adapter | The interface the editor UI uses for every host service (edits, files, dialogs, links, export). |
| Webview | The embedded browser panel that shows the editor UI inside VS Code. |
| No-op save | Opening a file and saving it with no content edits. |

Requirement keywords: "shall" is mandatory, "should" is recommended, "may" is optional. Priority follows the PRD: M (Must), S (Should), C (Could).

## 2. Overall description

### 2.1 Product perspective

amir_md is a new VS Code extension. It lives at `E:\PC3_Shared\Plugins\amir_marketplace\extensions\amir_md\`, next to the existing amir extension, and uses the same toolchain (REF-8): TypeScript in strict mode, esbuild bundling, packaging with `vsce`, and tests with `node --import tsx --test`.

The navigation pane is a port of the navigator prototype (REF-7): the tree built from the flat heading list with a level stack, the rotating triangle, the ARIA keyboard handling, the filter that saves and restores expansion, and the scroll-spy with breadcrumb. The prototype is read-only and generated by script; amir_md turns it into a live editor.

### 2.2 Architecture overview

```
VS Code
+-- Extension host (Node.js, TypeScript)
|   +-- AmirMdEditorProvider   CustomTextEditorProvider for *.md
|   +-- DocumentSync           TextDocument <-> webview edits, version handshake
|   +-- ResourceResolver       image paths -> webview URIs, localResourceRoots
|   +-- ExportService          PDF (puppeteer-core + system Edge or Chrome),
|   |                          DOCX (bundled docx library), optional Pandoc
|   +-- Contributions          commands, menus, keybindings, settings
|
+-- Webview (browser, TypeScript bundle)
    +-- Editor UI core (host-agnostic)
    |   +-- Toolbar            Word-style ribbon
    |   +-- NavPane            tree, filter, level controls
    |   +-- Editor             ProseMirror based document view
    |   +-- FoldManager        fold carets, fold ranges, fold state
    |   +-- MarkdownCodec      parse to document model, serialize, block source map
    +-- VsCodeHostAdapter      postMessage bridge to the extension host
```

For release 2, the desktop shell implements the same host adapter. The editor UI core does not change.

### 2.3 Main functions

1. Open a Markdown file as formatted, editable text.
2. Keep the file as the single source of truth and write back only what changed.
3. Show and navigate the heading tree.
4. Fold and unfold sections in the document.
5. Format text: styles, fonts, sizes, character formatting, colors, lists, tables.
6. Insert and edit links and images.
7. Export to PDF, Word, and Markdown.

### 2.4 User classes

| Class | Description | Key needs |
|---|---|---|
| Author | Writes and maintains long technical documents. | Editing fidelity, clean diffs, navigation. |
| Reviewer | Reads, makes small edits, exports and shares. | Folding, export quality. |
| Engineer | Edits documentation occasionally, any experience level. | A familiar toolbar, no Markdown knowledge required. |

### 2.5 Operating environment

| Item | Requirement |
|---|---|
| Host application | VS Code 1.74 or later (matches the amir extension). Other VS Code based editors may work but are not a release 1 target. |
| Operating system | Windows 10 and 11 (primary). macOS and Linux are supported for editing; PDF export there needs Chrome, Chromium, Edge, or Pandoc. |
| Runtime | The Node.js runtime bundled with VS Code for the extension host; the VS Code webview (Chromium) for the UI. |
| PDF export | Microsoft Edge (included with Windows) or Google Chrome. Pandoc optional. |
| Network | Not required. Remote images load only if the document uses them and the setting allows it. |

### 2.6 Design and implementation constraints

| ID | Constraint |
|---|---|
| CON-01 | TypeScript with `strict` enabled; ES2022 target. |
| CON-02 | Two esbuild bundles: the extension host bundle (`platform: node`, `format: cjs`, `external: ['vscode']`) and the webview bundle (`platform: browser`). |
| CON-03 | Packaged with `vsce package --no-dependencies`, so all runtime dependencies are bundled. |
| CON-04 | The editor UI core shall not import the VS Code API. All host calls go through the host adapter (Appendix F). |
| CON-05 | The VS Code `TextDocument` is the single source of truth for file content. |
| CON-06 | Runtime dependencies shall use permissive licenses (MIT, Apache-2.0, BSD, MPL-2.0), listed in a third-party notices file. |
| CON-07 | No telemetry. |
| CON-08 | Publisher `amir`, extension ID `amir.amir-md`, custom editor view type `amir_md.editor`. |

## 4. Markdown storage contract

This section defines exactly what amir_md writes to the file. It is the contract that keeps files clean and portable.

### 4.1 Principles

1. The written syntax is CommonMark plus the GFM extensions for tables, strikethrough, task lists, and autolinks (REF-4, REF-5).
2. Formatting that Markdown supports is written as Markdown.
3. Formatting that Markdown lacks (underline, colors, fonts, sizes, Title, Subtitle, alignment, image width) is written as inline HTML.
4. Blocks the user did not edit keep their exact original text (FR-SAVE-05).
5. Nothing is ever dropped. Anything the codec cannot represent becomes a source block (4.5).

### 4.2 Formatting to Markdown mapping

| Formatting in the editor | Written to the file |
|---|---|
| Normal text | Plain paragraph. |
| Heading 1 to Heading 6 | ATX heading: `#` to `######`, one space, the text. |
| Title | `<p data-amir-style="title" style="font-size:26pt;">Text</p>` |
| Subtitle | `<p data-amir-style="subtitle" style="font-size:15pt;color:#595959;">Text</p>` |
| Bold | `**text**` (per `amir_md.markdown.strongMarker`) |
| Italic | `*text*` (per `amir_md.markdown.emphasisMarker`) |
| Bold italic | `***text***` |
| Underline | `<u>text</u>` |
| Strikethrough | `~~text~~` |
| Inline code | `` `code` `` |
| Superscript, subscript | `<sup>text</sup>`, `<sub>text</sub>` |
| Font color | `<span style="color:#E53935;">text</span>` |
| Highlight | `<span style="background-color:#FFF59D;">text</span>` |
| Font | `<span style="font-family:'Segoe UI';">text</span>` |
| Font size | `<span style="font-size:14pt;">text</span>` |
| Several styles on one run | One span, properties in the order color, background-color, font-family, font-size. |
| Link | `[text](address)` or `[text](address "title")` |
| Image | `![alt](path)` or `![alt](path "title")` |
| Resized image | `<img src="path" alt="alt" width="480">` |
| Bulleted list | `- item` (per `amir_md.markdown.bulletMarker`) |
| Numbered list | `1. item`, keeping the list's original start number |
| Checkbox list | `- [ ] item`, `- [x] item` |
| Block quote | `> text` |
| Code block | Fenced with three backticks and an optional language |
| Horizontal line | `---` |
| Table | GFM pipe table with an alignment row |
| Hard line break | Backslash at the end of the line |
| Paragraph alignment | `<p style="text-align:center;">Text</p>` |

Title, Subtitle, and aligned paragraphs are HTML blocks, and CommonMark does not parse Markdown inside HTML blocks. Inline formatting inside them shall therefore be written as HTML tags: `<strong>`, `<em>`, `<u>`, `<s>`, `<code>`, `<span>`, and `<a href>`.

Example of the stored form of an assessment result:

```markdown
### Assessment Result

Status: <span style="color:#E53935;">**Critical**</span>

This configuration does not follow the recommended best practice.
```

### 4.3 Serialization rules

1. Line endings match the document's line-ending style. The final newline state is kept.
2. New blocks are separated by one blank line.
3. Characters are escaped only where they would otherwise change the meaning. Text such as `[{C-3101: Confirm the value}]`, `2.1.3`, or `file_name_here` is written as is.
4. Heading text is trimmed of leading and trailing spaces.
5. Numbered lists keep their original start number.
6. A mark boundary that CommonMark cannot express with delimiters (for example, bold that starts inside a word next to punctuation) is written with the HTML tag (`<strong>`, `<em>`).

### 4.4 Block source map and splice

1. After each parse, every top-level block records the start and end offsets of its source text.
2. When a block's content changes, it is marked dirty. Only dirty blocks are serialized again.
3. The webview sends the host one range replacement per dirty block (or per run of adjacent dirty blocks), based on the recorded offsets and the base document version.
4. After the host applies the edit, the offsets are updated from the applied change. A full re-parse happens only after an external change.
5. Inserted blocks are written with the blank-line rule in 4.3; deleted blocks remove their source range together with one adjoining blank line.

### 4.5 Source blocks

These are kept exactly as written and shown as source blocks (FR-EDIT-15):

- YAML front matter (`---` at the top of the file) and TOML front matter (`+++`).
- HTML blocks, except the recognized forms in 4.2 (Title, Subtitle, aligned paragraph, `img`, and HTML tables the table editor can read).
- HTML comments (`<!-- ... -->`).
- Link reference definitions and footnote definitions.
- Math blocks and any other syntax the parser does not model.

Inline HTML inside a paragraph that is not in the allow-list (4.6) stays in the paragraph as literal source text and is written back unchanged.

### 4.6 HTML sanitization for display

Inline and block HTML shall be sanitized before it is shown in the webview. Sanitization affects only what is displayed; it shall never change the file text of blocks the user did not edit.

| Allowed | Values |
|---|---|
| Tags | `span`, `u`, `s`, `del`, `sup`, `sub`, `mark`, `strong`, `b`, `em`, `i`, `code`, `kbd`, `br`, `p`, `a`, `img`, `table`, `thead`, `tbody`, `tr`, `th`, `td` |
| Attributes | `style`, `data-amir-style`, `href`, `src`, `alt`, `title`, `width`, `height`, `align` |
| Style properties | `color`, `background-color`, `font-family`, `font-size`, `font-weight`, `font-style`, `text-decoration`, `text-align` |
| Link and image schemes | `http`, `https`, `mailto`, relative paths, `#` fragments; `data:image/*` for images only |

Scripts, `iframe`, `object`, `embed`, `form`, event-handler attributes (`on*`), and `javascript:` URLs shall be removed from the display.

### 4.7 Portability note

GitHub and some other viewers remove `style` attributes. Colors, fonts, sizes, and Title and Subtitle sizing will show in amir_md, in exports, and in viewers that allow inline styles, but not on GitHub. Text content and all standard Markdown formatting stay portable.

## 5. External interfaces

### 5.1 User interface

The webview shows, from top to bottom: the toolbar, the breadcrumb, and the main area, which holds the navigation pane on the left and the document on the right, separated by a splitter. The PRD (section 6) shows the layout.

- Colors come from VS Code theme variables (for example `--vscode-editor-background`, `--vscode-editor-foreground`, `--vscode-focusBorder`), so light, dark, and high contrast themes work without extra code.
- The document column has a maximum reading width of about 80 characters for body text. Heading styles differ by level, following the prototype (REF-7).
- The toolbar uses `role="toolbar"`, with arrow keys moving between its controls.

### 5.3 Webview message protocol

All messages are JSON objects with a `type` field. Shared type definitions live in `src/shared/messages.ts` and are used by both bundles.

| Direction | Type | Payload | Purpose |

| Host to webview | `exportDone` | `ok`, `path`, `error` | Export outcome. |
| Webview to host | `ready` | none | The UI is loaded. |

| Webview to host | `log` | `level`, `message` | Diagnostics to the output channel. |

### 5.4 File system

- The extension shall read and write files only through `vscode.workspace.fs` and the `TextDocument`.
- It shall write outside the document only in two cases: saving images into the images folder (FR-IMG-03), and writing an export to the path the user chose.

### 5.5 Export engines

| Engine | Interface |
|---|---|
| PDF | `puppeteer-core` with `executablePath` set to Edge (for example `C:\Program Files (x86)\Microsoft\Edge\Application\msedge.exe`) or Chrome, headless, printing the rendered HTML with the page options. |
| Word | The `docx` library, in the extension host, from the serialized document model. |

## Appendix F. Host adapter interface

```ts
export interface TextChange { start: number; end: number; text: string; }

export type EditResult =
  | { ok: true; version: number }
  | { ok: false; version: number; text: string };

export interface ExportOptions {
  pageSize?: 'Letter' | 'A4';
  marginMm?: number;
  pageNumbers?: boolean;
  includeToc?: boolean;
}

export interface HostAdapter {
  applyEdit(baseVersion: number, changes: TextChange[]): Promise<EditResult>;
  resolveResources(paths: string[]): Promise<Record<string, string | null>>;
  pickImage(): Promise<string | undefined>;
  saveImage(data: Uint8Array, mime: string, suggestedName: string): Promise<string>;
  openLink(href: string): void;
  exportDocument(format: 'pdf' | 'docx' | 'html', options: ExportOptions): Promise<{ ok: boolean; path?: string; error?: string }>;
  saveViewState(state: { foldState: unknown; navState: unknown }): void;
  onExternalChange(listener: (text: string, version: number) => void): void;
}
```
