# amir_humanized

You are executing a **document-humanization** skill.

Make documentation read as if it was written and edited by an experienced human
engineer instead of generated by AI.

Target writing style:

* Natural
* Professional
* Direct
* Technically precise
* Easy to scan
* Easy to understand
* Appropriate for internal or customer-facing technical documentation
* Written in normal engineering language

The goal is **not** to rewrite everything.

Use a **minimum-change approach**.

If existing text already sounds natural, clear, professional, and human-written,
leave it unchanged.

Do not make changes simply because the skill was invoked.

This skill is **system-level**. It is not tied to any repository, product, or
working directory. It works with general technical documentation.

Supporting files (read when needed):

| Path | Purpose |
|------|---------|
| `rules.md` | Full humanization rules (verbatim) |
| `report_template.md` | Mandatory report structure |
| `scripts/humanize.py` | Validate, extract, apply, compare, report |
| `scripts/requirements.txt` | `python-docx==1.2.0` (PDF extract uses `pypdf` if present) |
| `README.md` | Installation and invocation |

## Invocation

```text
/amir_humanized <document_path>
/amir:amir_humanized <document_path>
```

Example:

```text
/amir_humanized c:/test/test.docx
```

`$ARGUMENTS` is the document path. Strip wrapping quotes. If the path is missing,
stop and ask for it. Do not invent a document.

Optional (only if the user asks):

* `--output <path>` — write the humanized document somewhere other than
  `<source_dir>/<stem>_humanized<ext>`
* `--project-root <path>` — override project-root detection

Supported input: `.docx`, `.md`, `.txt`. `.pdf` is supported as extract-only;
never edit a PDF in place. Write `<stem>_humanized.md` beside the PDF and warn
that PDF layout cannot be preserved.

### Step 1 — Init

```text
python <script> init "<document_path>" --project-root "<absolute project root>"
```

On validation failure: stop. Report the error. Create no output files.

Init prints JSON with `source`, `output`, `report`, `project_root`,
`extract_path`, `file_type`. Read `extract_path`.

### Step 2 — Humanize editable blocks

Read `rules.md` if you need the full rule text.

For each extracted block:

* `immutable` — do not change
* `editable` or `mixed` — review; change only if there is a meaningful
  improvement
* Before changing any sentence, ask: **Does this already sound like something
  an experienced human engineer would naturally write?** If yes, leave it
  unchanged

Write a changes file (JSON):

```json
{
  "changes": [
    {
      "id": "body:p:3",
      "original": "exact original text",
      "revised": "humanized text",
      "reason": "Removed AI filler"
    }
  ],
  "change_categories": [
    "Removed AI-style filler language"
  ],
  "potential_technical_issues": [],
  "warnings": [],
  "paragraphs_reviewed": 0,
  "changed": 0,
  "unchanged": 0
}
```

`original` must match the extracted block text exactly. Do not include
unchanged blocks.

### Step 3 — Apply, validate, report

```text
python <script> finalize "<document_path>" --project-root "<absolute project root>" --changes "<changes.json>"
```

If finalize reports integrity failures, correct or revert the offending
changes and run finalize again. Do not claim success with failed validation.

Never overwrite the source document. Never delete the original.

## Core editing principle

Change text only when there is a meaningful improvement in naturalness,
readability, clarity, conciseness, or technical-documentation quality.

Do not rewrite sentences merely to create differences from the source.

Do not optimize for the maximum number of edits.

Optimize for the **smallest number of justified edits**.

Technical meaning has **higher priority than humanization**.

---

## Rules (apply all)

1. **Em dashes in normal prose:** do not use `—`. Rewrite the sentence
   naturally (period, comma, parentheses, colon, or a split). Do not
   mechanically replace `—` with `,`. Leave em dashes inside immutable
   technical content (code, CLI, literal strings, API responses,
   configuration, URLs, product-generated output). After editing, searchable
   prose must have **zero** em dashes. Report:
   `Em dashes remaining in normal prose: 0`

2. **Remove common AI writing patterns** by rewriting the sentence, not by
   blindly deleting the phrase. Examples: `It is important to note that...`,
   `It is worth noting that...`, `It should be noted that...`,
   `This ensures that...`, `This allows you to...`,
   `In this section, we will explore...`, `In this section, we will discuss...`,
   `The following section provides...`, `This comprehensive approach...`,
   `This robust solution...`, `This seamless process...`, `By leveraging...`,
   `In order to...`, `When it comes to...`

3. **Avoid artificial contrast** unless the contrast itself is meaningful:
   `This is not just X, but Y.`, `Rather than simply doing X, this enables Y.`,
   `Not only does this provide X, but it also provides Y.`,
   `While X is important, Y is equally important.`

4. **Reduce unnecessary filler** adjectives/adverbs that add no technical
   value (`robust`, `comprehensive`, `seamless`, `powerful`, `sophisticated`,
   `critical`, `crucial`, `essential`, `streamlined`, `holistic`,
   `effectively`, `efficiently`, `significantly`, `extremely`). Keep them when
   they communicate meaningful technical information.

5. **Avoid excessive colon usage** in explanations. Colons remain appropriate
   for headings, labels, definitions, tables, technical syntax, commands, and
   lists.

6. **Use direct engineering language.** Prefer `Check the site status before
   troubleshooting.` Prefer verbs: Check, Verify, Open, Select, Review,
   Confirm, Run, Compare, Configure, Validate, Troubleshoot, Monitor,
   Identify, Test. Do not make simple actions sound academic or corporate.

7. **Avoid unnecessary formality.** Simple does not mean casual. Keep the
   documentation professional. Do not add jokes, casual commentary, personal
   opinions, marketing/sales language, fake quotations, unnecessary analogies,
   first-person commentary, AI disclaimers, or emotional language. Do not
   write `Let's take a look at...`, `Now let's dive into...`,
   `As you can see...`, `You might be wondering...`, `Luckily...`,
   `The good news is...`

8. **Avoid repetitive section introductions and wrap-up paragraphs** that
   only repeat the heading or the section. Keep an intro or summary when it
   provides context or operational value the heading does not.

9. **Avoid excessive bullet lists.** Do not convert explanatory prose into
   bullets merely to look organized. Preserve existing lists when they
   already make sense.

10. **Avoid repetitive sentence structures** only when the repetition makes
    the document sound unnatural. Do not introduce artificial variation when
    the existing structure is useful.

11. **Preserve technical meaning.** Do not modify technical content unless
    the user explicitly requests technical corrections. Preserve CLI, code,
    APIs, JSON/YAML/XML, Terraform, Python, PowerShell, Bash, product
    commands, configuration, IPs, prefixes, ports, protocols, URLs,
    filenames, paths, object/variable/env names, configuration values, error
    and log messages, UI labels, product/feature names, versions, IDs,
    UUIDs, and literal examples.

12. **Do not humanize code.** Treat fenced code, preformatted text, CLI,
    configuration, scripts, API payloads, command/log/error output as
    immutable. Do not "fix" spelling, capitalization, punctuation, or
    spacing inside technical content.

13. **Potential technical errors:** do not silently fix them. Preserve the
    original. Record: `Potential technical issue detected but not modified.`
    with enough location context. Do not claim an error without sufficient
    evidence.

14. **DOCX:** prefer editing existing paragraph/run content. Do not flatten
    to plain text and rebuild. Preserve heading hierarchy and styles,
    paragraph styles, font formatting, bold/italics/underline, numbered and
    bullet lists, tables and table formatting, hyperlinks, page/section
    breaks, headers/footers, captions, cross-references where possible,
    images, screenshots, diagrams, and embedded objects where possible.

15. **Images and embedded content:** do not modify unless required only to
    preserve them during processing.

16. **Tables:** humanize explanatory prose in cells. Do not modify literal
    technical values. Preserve rows, columns, cell relationships, order, and
    formatting as much as possible.

17. **Headings:** humanize only when clearly AI-generated, unnecessarily
    verbose, awkward, or difficult to understand. Preserve section numbers,
    heading hierarchy, and technical/product terminology.

18. **Grammar:** correct genuine grammar problems when doing so does not
    alter technical meaning. Do not overcorrect into academic English.

19. **Preserve author intent:** conclusions, recommendations, requirements,
    warnings, severity, technical intent, operational sequence, procedure
    order, scope, and meaning.

20. **No hallucination.** Never add technical facts that were not present in
    the source. Do not invent capabilities, requirements, limitations,
    commands, API behavior, best practices, prerequisites, troubleshooting
    procedures, or explanations.

21. **Second-pass validation** is mandatory. Check for changed technical
    meaning; modified commands/config/code; corrupted URLs; changed IPs,
    ports, filenames, object names, product terminology, UI labels; broken
    numbering or bullets; missing or duplicated sections/paragraphs; missing
    or damaged tables; missing images; formatting damage; accidental removal
    of technical details; new unsupported technical statements; unnatural
    sentences introduced during humanization. Correct or revert problems
    before final output.

22. **Source-to-output integrity:** no sections, procedures, commands, code,
    API examples, technical values, URLs, images, or tables may disappear.
    Procedure order, heading hierarchy, and numbering must remain valid.

## Paths

Never overwrite the source. Default humanized document stays in the **same
directory as the source**:

| Input | Output document | Report |
|-------|-----------------|--------|
| `c:/test/test.docx` | `c:/test/test_humanized.docx` | `<PROJECT_ROOT>/.ai/reports/test_humanized_report.md` |
| `c:/docs/design.md` | `c:/docs/design_humanized.md` | `<PROJECT_ROOT>/.ai/reports/design_humanized_report.md` |
| `c:/docs/notes.txt` | `c:/docs/notes_humanized.txt` | `<PROJECT_ROOT>/.ai/reports/notes_humanized_report.md` |

The report **always** belongs under `<PROJECT_ROOT>/.ai/reports/`. Create that
directory automatically. Do not place the report next to the input, inside
the skill directory, or in a temporary directory.

Project-root priority (the script implements this; pass `--project-root` when
the environment already knows the workspace root):

1. Explicit `--project-root` / environment project root
2. Current IDE or workspace root
3. Git repository root
4. Current working directory only if no better information exists

If `_humanized` output already exists, replace it only after successful
processing (atomic write). Never overwrite the source.

* Report the actual error
* Do not claim success
* Do not fabricate validation results

If formatting preservation cannot be guaranteed, state that clearly.

If a specific document element cannot be processed safely, preserve it rather
than attempting a risky transformation.
