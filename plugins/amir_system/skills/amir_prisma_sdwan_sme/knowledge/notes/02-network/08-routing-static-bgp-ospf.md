# Routing: branch and data center models, static routes, BGP, OSPF, route maps, redistribution

Domain: 2 | Applies to: Admin Guide May 2025; LAN dynamic routing from 5.2.1; OSPF from 6.4.1; BGP router ID per VRF from 6.6.1 (internal) | Status: EVIDENCE REVIEWED | Last updated: 2026-10-08

## Explanation (plain words)

The controller is the routing brain of the fabric: anything a site learns and marks **Global** is sent to the controller and distributed to the other sites as "WAN paths"; **Local** keeps it on the box. At a **branch**, the ION can be the LAN default gateway or peer with a Layer 3 switch (BGP or OSPF) and can peer with the MPLS edge router. At a **data center**, the ION sits off-path and uses BGP to attract branch-destined traffic from the **core** router by injecting more specific routes, optionally peering with the WAN **edge** router for the MPLS underlay. Three BGP "peer types" exist on DC IONs (core, edge, classic) and the controller auto-generates route maps for core and edge peers.

## Branch routing (official pp. 370–371)

- Static and dynamic routing on Internet, private WAN underlay, LAN and standard VPNs. Static routes can point at a standard VPN interface or its peer IP.
- Private WAN underlay uses a bypass pair by default (bridging); an L3 interface needs **L3 Direct Private WAN Forwarding**. **LAN dynamic routing from 5.2.1** needs both L3 Direct Private WAN Forwarding and **L3 LAN Forwarding**; the latter cannot be enabled while Private L2 bypass pairs exist (5.2.3+ shows a message).
- Branch IONs support **classic peers only**; multiple peers, even on one interface. Each underlay and standard VPN is a separate routing domain: routes learned in one are not advertised into another, so the branch never becomes a transit point.
- Deployment models: Layer 2-only (no routing; Internet on ION, MPLS on router), Layer 2/Layer 3 (L3 WAN interface sources a private-WAN VPN; BGP to router), router replacement (ION terminates MPLS and Internet; BGP with PE), LAN-side BGP (learn prefixes behind L3 switch; advertise WAN-learned prefixes or default to the LAN; advertise LAN prefixes to other sites).
- Deck: route preference order Directly Connected > Static > eBGP > OSPF > iBGP (TSE OSPF playbook; internal).

## Data center routing (official pp. 372–373)

- Static routing on all interfaces; dynamic routing only on **Peer with a Network** and standard VPN interfaces, not on Internet-facing ports. Off-path insertion: the DC ION attracts only traffic to branches with an active VPN by injecting more specific or preferred routes toward the core. Peer types core, edge, classic in a single routing domain; configure local/remote AS, peer IP, MD5, timers; route-map generation, updates and filtering are automatic for core/edge.
- Topologies: edge and core; core only (no private underlay exit); core with the DC ION as WAN edge (peers with core and PE); core and standard VPN peers.
- **Host tracking** (pp. 400–401): ICMP tracker IP(s) reached through the core; while reachable, branch traffic stays on active paths; when it fails, active/backup paths switch and traffic reroutes to alternative overlay paths in the same DC. Global VRF only.
- **Distribution to Fabric** (p. 399): choose which branch sites receive DC-learned prefixes; WS-001 adds that BGP/OSPF-learned DC LAN routes are **not** auto-distributed to branches (explicit configuration), whereas global static routes and site prefixes are.
- **Intra Cluster Tunnel** (pp. 392–393): when both DC IONs advertise the same aggregate, the core may ECMP to the ION that lacks the active VPN; set the tunnel peer so misrouted traffic is forwarded to the peer DC ION that has the active VPN. Also covers standard-VPN asymmetry (route map on the standard VPN peer to prefer that path for the return).
- TSE BGP playbook (internal): if the single **core peer** goes down, all fabric VPNs on that DC ION become unusable (forcing switchover); a **classic peer** failure does not affect VPN usability and can black-hole traffic, so core peers are recommended. The DC injects branch prefixes with the mask lengthened by one (/24 → /25) and the `no-advertise` community toward the core; use a route map (for example `CG-ADVERTISE`) to stop those from being redistributed into OSPF/EIGRP. Routes from the edge peer without at least two ASNs in the AS path are ignored (an implicit default toward the core exists).

## Static routes (pp. 374–376)

- Per VRF (Global default; IPv6 in Global VRF from 6.2.3; global and link-local IPv6 from 6.0.1); destination prefix; **NextHop Reachability Probe** (ICMP every second, 100 ms wait, 3 consecutive failures ⇒ next hop unreachable and route removed; one probe per distinct next hop; not available when the next hop is an interface, Self is true, or recursive next hop on a DC ION; status via the route's ellipsis menu); scope Local/Global (global static routes are advertised to other sites automatically); next hop IP (IPv4, global IPv6, or link-local plus interface) **or** interface (ARP generated directly), not both; **admin distance default 1** (lower preferred; equal distance ⇒ only one next hop used; failover to alternates; last next hop failure drops flows and shows in analytics); Self flag.
- WS-001: at DC/hub sites add a static default to the core peer with higher admin distance than the BGP default plus next-hop probe as a safety net; set Global scope only when remote sites need the route (wrong Local scope is the most common routing issue).

## BGP (pp. 377–399)

- Prerequisites: L3 forwarding toggles as above (not needed for BGP on Internet or standard VPN). **Global parameters**: Local AS (1–4294967295 or A.B), MD5 secret 1–32 chars, router ID (IPv4), **prefix advertisement to LAN** (Default 0.0.0.0/0 and ::/0 [default], Unaggregated, Auto-Aggregated) and **to WAN** (None [default], Unaggregated, Auto-Aggregated, Manually Aggregated, Manual Summary Aggregate Only); advanced: keepalive 3–200 s (default 30), hold 3–600 s (default 90, ≥3× keepalive), multihop 1–255 (default 1), max paths 1–255 (default 1), advertise interval 0–300 s (default 1), peer retry 0–65535 s (default 120), graceful restart off by default, stale path 1–3600 s (default 120), **admin distance default 20** for learned prefixes (a static route's distance overrides BGP's).
- A branch does not re-advertise routes learned from one peer to another; it advertises only LAN networks, static routes and interface addresses, and only with **Global** scope on the peer.
- **Scope table for branch peers** (p. 388): Local on either side ⇒ learned routes are not advertised to other peers or the controller. Global WAN-side peer: advertises global connected subnets, global static routes and routes learned from global LAN peers; learned routes go only to global LAN-side peers, not to other WAN peers nor the controller. Global LAN-side peer: advertises global connected/static routes and routes from global WAN and LAN peers; learned routes go to all WAN-side peers, other global LAN peers, **and the controller** (remote sites). A LAN-side peer gets only the default route when the LAN advertisement setting is Default.
- **Peer configuration** (pp. 389–392): VRF; peer IP (IPv4/IPv6); remote AS; update source IP (multi-hop); router ID (**must be the same for all peers in a VRF**, may differ across VRFs; different IDs cause flapping); peer type (DC only; core/edge auto-generate route maps, cloneable); scope; shutdown; route prefix type IPv4/IPv6/both; prefix advertisement (manual or auto aggregation, prefix lists, route map in/out, advertise default to peer; note on identical aggregates on both DC IONs and the tunnel peer address); per-peer overrides (keepalive 3–60 s, hold, advertise interval 0–600 s, retry, multihop, MD5, local AS).
- **Route maps** (pp. 393–396): one route map per peer (same map can serve in and out); entries ordered 1–65535 with **99–103 reserved for auto-generated maps**; permit/deny; continue; match prefix list, community list, AS path list, IP next hop; set AS path prepend, weight, local preference, community, additive community, next hop (peer-address / ipv6-peer-address / explicit); IPv4 and IPv6 need separate entries with continue. Redistribution: BGP/connected/static into OSPF and OSPF/connected/static into BGP (IPv4).
- Prefix lists, AS path lists (regex), IP community lists (pp. 396–398).
- **Status** (pp. 398–399): per peer status, statistics, received/advertised/discovered prefixes; **hard reset** (tear down TCP, flush) vs **soft reset** (refresh without teardown); reset not valid for classic peers. `Monitor > Activity > Routing` shows peer type, state, uptime/downtime, advertised and reachable prefixes (edge peers show reachable only; DC advertises branch prefixes to classic and core peers, not edge).
- WS-001 (internal): MD5 on all peers; configure edge peering only when native MPLS underlay forwarding is needed; soft reset after changing filters; **BGP router ID per VRF from 6.6.1** (global per VRF instead of per peer).
- TSE BGP playbook (internal): triage checklist (local AS, MD5, remote AS, peer IP, shutdown flag, router ID per VRF, scope, prefix advertisement to WAN not None); dual blended Internet with provider-independent prefix recipe (5.0.3+, NONAT on both Internet interfaces, inbound map allowing only default, outbound map allowing only the PI block, open TCP 179 inbound via the advanced menu); flow browser shows "path change: asymmetry" when return traffic arrives on the other circuit; branch routes lost after MPLS outage ⇒ ingress route map on the branch CE dropping DC-advertised local prefixes; external router gotchas (NX-OS needs `address-family ipv4 unicast` under the neighbor; HP needs `enable`; Brocade and EIGRP route-map examples). CLI set: `dump routing summary|cache|peer status|peer config|peer neighbor-stat|peer received-routes|peer routes|peer route via|peer route json|running-config|peer advertised-routes`, `clear routing` (caution).

## OSPF (pp. 378–382; TSE OSPF playbook)

- **6.4.1+**, OSPFv2 (RFC 2328, IPv4), LAN side at branch (toward L3 switches) and at campus/DC aggregation (hub: on "Peer with a Network" interfaces); FRR OSPF daemon programmed by the ION route manager; L3 mode only; not on SVIs (WS-001); branch LAN runs either OSPF or BGP, not both on the same segment; BGP on WAN with OSPF on LAN is fine.
- Infra settings: router ID; MD5 key ID 1–255, key ≤16 chars; LAN prefix advertisement Default / Unaggregated / Auto-Aggregated (spoke only); cost 1–65535; hello 1–65535 (default 10); dead 1–65535 (default 40; must be ≥2× hello); retransmit (default 5); transmit delay (default 1). OSPF configuration per VRF: name, router ID, LAN prefix advertisement (+ route map for unaggregated/auto), **Redistribute BGP**, scope, shutdown; area ID (x.x.x.x), type Normal / Stub / NSSA, interfaces, per-interface overrides. Discovered neighbors view. CLI: `dump routing ospf vrf <vrf|all> configs|discovered-neighbors|reachable-prefixes|routes|database|interface statistics`, `clear routing ospf`.
- Behavior (playbook): spoke OSPF-learned prefixes go to the controller and hubs as learnt prefixes (`inspect wan paths` shows them as WAN paths); hub advertises controller-provided WAN paths as external prefixes; only in-path, no prefix splitting; global static routes are redistributed into OSPF (and BGP) by default; route-map match "metric" and set "type" (1/2) and "metric" for redistribution; downgrade from 6.4.1 requires removing OSPF config; route manager log `/log/syslog/rtr-mgr`.

## Route manager internals (PAEE, internal)

Reads config DB (interfaces, static routes, BGP, WAN paths), builds state DB and FIB databases (fib/vpn, fib/lan, fib/route_leak), asks the FIB manager to resolve static and connected routes, programs kernel rules/routes and FRR. Controller side: the Rhea service turns route configuration into **wanpaths** pushed to the element through Elapi (`wanpathsbulk` PUT; prefix sets stored in Redis config DB 11; state DB wiped on reboot). Threads: config, backend (wanpath/static/OSPF/interface/element state), monitor probe/static, data publisher (BGP peer status, reachable/advertised, next-hop reachability). `wan_path_update` triggers on interface IP/scope change, static route change, BGP learned route change, HA status change. Duplicate prefixes from two sites show `add_branch_prefix_route … File exists` in `rtr-mgr` logs; withdraw of a prefix still used by another site is skipped. Kernel table 2010 holds the all-peer-in routes (`ip route show table 2010`).

## Addendum 2026-10-08 (B20: KG-079 PARTIAL)

Design Guide Oct 2025 (SRC-000038 pp.51–54, VERIFIED): BGP on IONs is **eBGP only**; peer types Classic (both site types, no auto route-maps), Core (DC only, auto route-maps, advertises only prefixes of currently connected branches; **core peer down → all fabric links to the DC marked unusable**, with several peers one up suffices), Edge (DC only, listen-only). **Prefix splitting**: when a connected branch prefix equals an edge-learned prefix, the DC ION advertises longer matches (10.130.0.0/21 → 10.130.0.0/22 + 10.130.4.0/22) so the core prefers the SD-WAN path. The internal "/25 injection with no-advertise community" claim is therefore partly corroborated (longer-match injection) but the /25 length and the community remain UNVERIFIED. Recommended DC BGP timers keepalive 1 s / hold 3 s with MD5 (SRC-000037 pp.53–54). Options: Force VPN to VPN Traffic to Local Next Hop (DC), L3 Direct Private WAN Forwarding and L3 LAN Forwarding (branch), Application Reachability Probe source interface.
