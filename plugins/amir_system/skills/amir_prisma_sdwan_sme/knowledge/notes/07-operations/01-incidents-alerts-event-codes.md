# Incidents and alerts: model, correlation, lifecycle, incident policies, event codes

Domain: 7 | Applies to: Incidents and Alerts guide (WS-041, Nov 2023/2025 reprint, 92 pp.), Admin Guide May 2025 (Site Summary, dashboards), WS-030 Day 2 draft §2.12/§3.3 (cross-checked), WS-033 deck slides 406–421, release notes 6.3.2 (retired codes), 6.4.1/6.4.2 (policy selectors) | Status: DOCUMENTED | Last updated: 2026-10-08

## Explanation (plain words)

An **alert** says a threshold or component event happened and may or may not be a fault; an **incident** says there is a fault and has a life: raised, standing, cleared. Each has a **severity** fixed by the product (Critical: network or part of it down; Warning: impacts the network, needs immediate attention; Informational: degraded, attention soon) and a **priority** P1–P5 that comes from a severity-to-priority mapping and can be changed by **incident policy**. The controller **correlates** related faults so one Secure Fabric link incident replaces many VPN-link incidents, and suppresses children under a parent (site down, interface down, circuit performance degraded). Planned maintenance is handled with scheduled suppression rules; there is no "maintenance mode".

## Documented model (WS-041 pp.5–10, 25–28)

- Filters: Show Resolved, Include/Show Only Acknowledged, Include/Show Only Suppressed; sort by time or severity; by site (name, traffic volume, init/transaction failure, branch/DC, admin state), severity, priority P1–P5, **category** (Network, Device, Cellular, Application, Policy, Branch HA, Authentication, User ID), code, time, **Correlation ID** (one ID per raise/clear pair; survives the clear). Acknowledge / Unacknowledge (bulk) only on unresolved incidents.
- **Incident synchronisation**: the device sends standing-incident snapshots every **24 hours**; the controller clears what no longer exists and raises what is missing; manual `Sync Incident` from the device menu.
- Correlation examples: multiple VPN-down incidents become one Secure Fabric Link incident; VPN link codes `NETWORK_VPNBFD_DOWN`, `NETWORK_VPNLINK_DOWN`, `NETWORK_VPNPEER_UNAVAILABLE/UNREACHABLE`, `NETWORK_VPNSS_UNAVAILABLE/MISMATCH` aggregate into `NETWORK_SECUREFABRICLINK_DOWN` (Warning, all VPN links of a link down) or `_DEGRADED` (Informational, some up some down); underlay codes `DEVICEHW_INTERFACE_DOWN`, `NETWORK_DIRECTINTERNET_DOWN`, `NETWORK_DIRECTPRIVATE_DOWN` suppress the fabric incidents that depend on them; **Admin Down** on an interface suppresses its fabric incidents (shown in the Reason field); a parent interface down suppresses its logical interfaces' incidents.
- **Site connectivity (from 5.5.1)**: `SITE_CONNECTIVITY_DOWN` at a DC = all fabric links down; at a branch = all fabric links down **and** all devices disconnected from the controller for **more than 10 minutes**; clears when one VPN is up. `SITE_CONNECTIVITY_DEGRADED` = Direct Internet or Direct Private down, or at least one fabric link or service link down; clears when all WAN paths are up.
- **Service endpoint (from 5.6.1)**: `NETWORK_STANDARD_VPN_ENDPOINT_DOWN` raised by the controller when `DEVICEHW_INTERFACE_DOWN` exists on at least two standard VPN interfaces to the same endpoint (not raised for peer destinations, admin-down parents, parents without WAN label, parent op-down, device disconnected, L3 reachability issue on parent).
- Category descriptions (p.25–27): hardware (PSU failure Warning, DIMM failure Critical, disk SMART alert, disk IO failure Critical), software (module fail Incident, high CPU/disk alerts, corrupt DB Incident), interface (down Warning, excessive errors Alert), registration (CIC channel failure Warning, inventory retrieval failure Warning), BGP peering (WAN edge / core peer down Warning; routes from WAN edge indicate private WAN down), site level (direct Internet / private WAN unavailable Warning; all paths unavailable Critical; loss of connectivity Critical; path labels missing for policy).
- **High temperature** (`DEVICEHW_TEMPERATURE_SENSOR`, ION 1200-S-5G: CPU, ACPITZ, cellular modem, PSE sensors; 5-minute sampling; CPU high for 3 consecutive readings → shutdown; two non-CPU sensors over threshold 3 of 5 readings → shutdown; clear may take up to 25 minutes; thresholds CPU 90 °C, ACPITZ 67 °C, modem and PSE outside −30…105/115 °C; PoE shut at CPU 85 °C, resumes at 75 °C; RF suspended at 118 °C; device shutdown above 135 °C; manual power-up after a thermal shutdown).
- **SNMP trap correlation** (p.21–22): `DEVICEHW_INTERFACE_DOWN` ↔ linkDown/linkUp; `DEVICESW_GENERAL_PROCESSRESTART` ↔ cgxProcessStop/warmStart; `NETWORK_DIRECTINTERNET_DOWN` ↔ cgxPublicWanDown/Up; `NETWORK_DIRECTPRIVATE_DOWN` ↔ cgxPrivateWanDown/Up; `NETWORK_PRIVATEWAN_DEGRADED/UNREACHABLE` ↔ cgxPrivateWanDegraded(Clear)/Unreachable(Clear); `NETWORK_VPNBFD_DOWN` ↔ cgxVpnBfdDown/Up; `NETWORK_VPNLINK_DOWN` ↔ cgxVpnLinkDown/Up; `NETWORK_VPNPEER_UNREACHABLE` ↔ cgxVpnPeerUnreachable(Clear); the VPN codes can be suppressed by Secure Fabric Link incidents.
- **Troubleshooting steps per code** (pp.11–19) exist for about 35 codes, e.g. `DEVICESW_DISCONNECTED_FROM_CONTROLLER` (site connectivity, process incidents, firewall rules, controller maintenance, then Support), `DEVICESW_IMAGE_INCOMPATIBLE` (version not on the available list → upgrade/downgrade then "Recheck SW Version"), `DEVICEHW_DISKENC_SYSTEM` (re-upgrade/downgrade cycle), `NETWORK_DIRECTINTERNET_DOWN` (interface incidents, ping public IPs, `inspect system arp`, capture, modem power cycle), `NETWORK_PRIVATEWAN_UNREACHABLE` (DC only; `PEERING_EDGE_DOWN` first), `SPOKEHA_*` (effective priority zero, tracked interfaces, services, control interface VLAN), `SITE_CIRCUIT_ABSENT_FOR_POLICY` (assign the missing labels).

## Incident policies (WS-041 pp.85–91; 6.4.2 adds All Incidents / All Alerts selectors)

Up to **16 policy sets** (one active per site), **128 rules** per set, explicit order (a rule without an order number does not execute). Rule parts: resource type (Application Definitions, BGP Peers, Cellular Modules, Circuits, Devices, Interfaces, Path Policy Sets, QoS Policy Sets, Secure Fabric Links, Service Endpoints, Sites) with optional sub-type (e.g. Circuits → Public/Private) and specific resources; event codes by category (Application, AAA, Device, Network, Policy, Spoke HA Groups) or All Incidents / All Alerts; optional schedule (start/end MM/DD/YYYY HH:mm); actions **Suppress** Yes/No/Default, **Priority** P1–P5, **dampening** 5 minutes–7 days (incident suppressed until the interval ends, then unsuppressed if still standing; incidents only, not alerts); escalation **Standing rule** (time threshold → new priority) and **Flap rule** (rate 2–512 within a duration → new `FLAP_RATE_EXCEEDED` incident). Severity mapping editable per set (`Edit Severity Mapping`). Use cases: business-intent priority (BGP peer down branch P2→P1), escalate standing (device disconnected >24 h), maintenance-window suppression, Internet-outage suppression, flap detection (standard VPN to Prisma Access 3×/hour), staging and unstable-LTE suppression.

## Internal (deck 406–421; WS-030 §3.3)

ML-based correlation needs no configuration; dampening introduced 6.3.1 listing (WS-021 FEATURE-005); default child suppression (e.g. `APPLICATION_PERFORMANCE_DEGRADED` under `CIRCUIT_PERFORMANCE_DEGRADED`) is changeable in incident settings; the consolidated SCM `Incidents > Incidents` page adds a cross-product Summary (severities Critical/High/Warning/Informational), Notification Profiles (email, webhooks, integrations, ServiceNow), Settings and Informational Alerts; the Day 2 draft recommends notifying by priority, paging P1/P2 only, one incident one ticket, and scheduled suppression for maintenance.
