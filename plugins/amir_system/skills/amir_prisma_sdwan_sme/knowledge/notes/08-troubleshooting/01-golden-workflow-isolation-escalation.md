# Troubleshooting method: isolation order, evidence, escalation data, RMA triage, case taxonomy

Domain: 8 | Applies to: TSE playbooks General Isolation 175768189 (2024-02), Element Troubleshooting 700294090 (2026-01), DIT Playbook 295179659 (2026-03), RMA 175768010 (2024-02), Taxonomy 236810084 (2024-07); WS-030 Day 2 draft ch.4–5, 10.7, 11 (2026-09); Incidents and Alerts guide (WS-041) | Status: INTERNAL METHOD, corroborated by official incident/troubleshooting chapters | Last updated: 2026-10-08

## Explanation (plain words)

Every Prisma SD-WAN fault is isolated from the outside in: **scope** (one user, one site, many sites, everything), then **what the controller already knows** (incidents for the site and window), then the site's layers in dependency order **device → controller connectivity → circuits → Secure Fabric → routing**, then the **flow** itself (which application, policy, path, security action, decision data), then the **domain** that owns the fault (client/LAN, ION, carrier, fabric, data center, policy, security service, Prisma Access/SaaS). Only then decide to fix, work around or escalate, and validate with the same screens and filters that found the problem. Observe before you change; collect evidence first.

## Isolation order (General Isolation playbook, Day 2 ch.4; both agree)

1. **System-wide**: portal access, roles, API tokens, audit log (System Administration / User Administration in legacy terms; `System Settings` in SCM). Check the Prisma SASE service status page when many sites go offline at once.
2. **Site-wide**: link status Physical / Secure Fabric / Standard VPN, device online/offline, standing alarms, Activity charts (bandwidth, transactions, app health, response time, flows), media analytics, link quality, flow browser, routing stats. Policies bind only to branch sites, not DC sites (playbook note).
3. **Device**: online; ports configured with the right LAN/Public/Private designation; LAN networks with correct scope (Local/Global) and tags; routing scope; HA priority, control interface and tracked interfaces.
4. **Path**: overlay (branch-to-DC, branch-to-branch, standard VPN) vs underlay (L3 reachability: Internet uses passive and active monitoring; private WAN uses active monitoring plus BGP prefix learning).
5. **Fabric VPN**: VPN admin up at both ends; DC has at least one Internet circuit with a public label and admin up; `dump vpn summary Status=Down`, `dump vpn status VpnID=<id>`; check BFD; possible causes: peer unreachable, admin down, IPsec phase 1/2 failure, BFD failure, stale ISP-modem NAT entries; tcpdump both ends for ISAKMP and ESP; `file tailf log vpn`; cipher settings must match (`Site > Advanced > Configure Ciphers`); public VPNs auto-provision branch-to-DC when both sides carry a public label; private VPNs only when the **same private label** is on both ends; branch-to-branch VPNs are manual; confirm bidirectional **UDP 4500**.
6. **Routing**: AS number, peer IP, multihop; DC peer type (core / edge learns only / classic needs manual route maps); static route admin distance, next hop, scope; prefix split/no-split; after BGP global/advanced changes do a soft reset; expected behaviour: a prefix learned from the edge peer that is also a Global branch prefix is split and advertised to the core peer with the **no-advertise** community; with only a core peer the branch prefix is advertised as received; a classic peer can make the DC ION a transit device unless route maps prevent it; branch traffic fails if the branch prefix is Local instead of Global.
7. **Application**: Flow Browser filtered by site/IP/app → flow detail → path policy set/rule and security rule/action; deny → fix security rule; otherwise check path rule paths.

## Device-level quick checks (Element Troubleshooting playbook, 2026)

- Offline device: `dump overview` (Controller Connection, Registration State, MIC and Claim certificate validity), `dump controller status` (control plane over 443), `debug controller reachability <interface>` (MIC/CIC verification vs curl connection). Offline devices have no remote toolkit: console on the AUX port **115200/8/N/1**; devices without a controller port use port 1 or 2 on a DHCP Internet network for first connectivity. Limits: **10 concurrent operator CLI sessions per device, 30 per account**.
- Processes: `debug process status all|name=<p>`; critical processes `dns` (module lookups such as locator.cgnx.net), `elapi` (element-controller API, config mismatch), `fc` (flow controller: policy, QoS, ZBFW; must be RUNNING and not restarting; restarting it interrupts traffic), `mrl_agent` (controller connectivity; logs in `/log/syslog/mrl_agent`).
- Performance policy: `inspect performance-policy incidents type link-quality circuit=<id> details` (EMA bad-sample percent, Alarm Standing), `inspect performance-policy lookup application=<id>`, `inspect performance-policy fec status`; FEC only on fabric VPNs for 1–10 % loss; unsupported function → whole rule ignored; rule limits ION 1000 = 30, ION 9200 = 255.
- BGP: `dump routing summary` (State/PfxRcd), `dump routing peer neighbor`, `clear routing peer-ip <ip> soft` (policy re-evaluation without tearing down TCP); L3 Direct Private WAN Forwarding and L3 LAN Forwarding both needed for dynamic LAN routing; route maps auto-generated for core/edge peers, manual for classic.
- Path selection: `inspect flow-detail srcv4= dstv4=` (WANPATH-ID, PATH such as `lan_to_public_vpn`), `inspect network-policy lookup application=`; Flow Decision Bitmap in the UI explains exclusions ("Excluded WAN Paths: High Packet Loss"); L3 failure paths only for total L3 loss.
- Switch/PoE (1200-S, 3200): `dump switch port status`, `dump poe system status`, `debug poe interface <id> restart`; changing ION 3200 L2↔L3 mode **wipes ports 5–10 configuration**; PoE ports 7–10 default 100 % (60 W) threshold; up to 10 LLDP neighbours shown per interface; many interfaces degrade SNMP response on small models.

(Internal process; the skill should only say "open a TAC case with the tech-support bundle".)
- RMA triage questions (RMA playbook): age in service, power events/environment, UPS, UI alerts; power cable/outlet, cold boot, boot loop, LEDs, console errors, bypass setup, `DEVICEHW_POWER_LOST` (external PSU models 7000/9000); fans/airflow/dust; cable, link LEDs, single-port isolation, neighbour device status, `dump overview` / `dump device info`; firmware reinstall; cellular `dump cellular status cwan1`. ## Legacy knowledge-base articles still useful for mechanics (CGXKB 2016–2019; commands OBSOLETE, behaviour largely unchanged)

- **Flow path shows "NA"** (74187102): either dropped by ZBFW (middle-of-flow: the Advanced Info `SYN client→server` counter is 0, no handshake seen) or **bridged**. Bridged causes: LAN-side IP not in a configured LAN prefix (unknown prefix), broadcast, multicast, BFD. The official Incidents guide repeats the unknown-prefix bridging symptom (an interface without a circuit label also bridges).
- **VPN alarm meanings** (74187094): `NETWORK_VPNSS_UNAVAILABLE` = device out of shared secrets → check controller connectivity; `NETWORK_VPNSS_MISMATCH` = peers disagree on the shared secret → clock skew; `NETWORK_VPNPEER_UNREACHABLE` = peer unreachable → firewall/NAT; `NETWORK_VPNBFD_DOWN` = control up but data path down → firewall. Required through firewalls: **UDP 4500** and **ESP (protocol 50)**. NAT matrix: public–public, public–DNAT, public–SNAT need nothing; DNAT–DNAT needs NAT on one side; DNAT–SNAT needs it on the DNAT side; SNAT–SNAT not supported. VPN shim addresses (100.64.x.x) identify the BFD session that belongs to a VPN link.
- **Media calls** (74187035, 2018): jitter 20–30 ms delays phone calls, above about 50 ms calls drop; soft clients tolerate 20–50 ms and renegotiate codecs, real impact above about 70 ms; loss above 3 % degrades MOS, above 10 % calls drop; check control and data channels are both custom-defined with the same priority, that RTP data channels are associated with the parent app, and that audio/video queues (non-work-conserving, P1–P4 audio and video) are sized.
