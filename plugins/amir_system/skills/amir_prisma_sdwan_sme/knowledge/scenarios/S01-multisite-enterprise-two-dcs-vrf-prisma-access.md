# S01 — Multi-site enterprise: 40 branches (MPLS + Internet + LTE), two DCs, BGP to core, VRF segmentation, Prisma Access DIA

Domains: 1, 2, 3, 4, 9 | Evidence type: SCENARIO | Written 2026-10-08

## 1. Situation

40 branches, each with one MPLS circuit (single carrier), one or two Internet circuits (cable/fibre), and an LTE modem (metered). Two data centers (East, West) with existing core routers and MPLS CE routers; servers behind both. Segments wanted: corporate, IoT, guest. Internet access must be inspected by Prisma Access. Target software: ION 6.5.x (Gen-2 hardware: 1200-S at branches, 5200 at DCs).

## 2. Question

Design the fabric, routing, segmentation and Prisma Access integration; walk the packet path for branch→DC, branch→SaaS and branch→branch; explain what happens when (a) MPLS degrades, (b) a DC ION fails, (c) a Prisma Access tunnel drops.

## 3. Reasoning chain

1. **Sites and clusters.** Two DC sites, each with a pair of ION 5200 in the automatically created cluster; 40 branches map to the default cluster of each DC (one cluster is enough; a soft limit is optional). DC IONs integrate off-path, not inline. [VERIFIED — notes 02-network/06 (SRC-000029 pp.85–89), 10-design/01 (SRC-000038 pp.40–42)]
2. **Domains and groups.** Domains East/West; groups Primary-DC and Secondary-DC with per-domain membership so one policy resolves regionally. Every branch bound to a domain. [VERIFIED — 03-application-traffic/03 (SRC-000029 pp.470–476); 10-design/02 (SRC-000037 pp.35–37)]
3. **Circuits.** One category per circuit per site (MPLS; Ethernet Internet / Internet Cable; Metered 3G/4G/LTE). MPLS WAN network identical at branches and DCs so private overlays auto-form within the same category. LTE: "Minimize metered LTE" recipe (cost 129, keep-alive 600,000 ms, no controller/probe use) and the category only as an **L3 Failure** path. [VERIFIED for the recipe and the same-category rule — 03-application-traffic/02 (SRC-000029 pp.456–459), 10-design/01 Table 7; CORROBORATED for the matching WAN network — 02-network/01]
4. **Overlay.** In control mode each branch builds fabric VPNs to both DC IONs of its cluster over every public circuit (all-to-all) and over MPLS (same category). Branch↔branch is via a DC unless explicit branch links exist. Each branch has one active DC ION per DC (first link up); size each DC ION to carry all 40 branches alone. [VERIFIED — 10-design/01 (SRC-000038 pp.32, 40); 02-network/06]
5. **DC routing.** Core peer from each DC ION to each core router, eBGP, MD5, keepalive 1 s / hold 3 s; optional edge peer to the MPLS CE (listen-only) when fabric over MPLS is wanted. Each DC ION needs a default or WAN-summary route to the core. Prefix splitting applies if an edge-learned prefix equals a connected branch prefix. [VERIFIED — 02-network/08 addendum (SRC-000038 pp.51–54; SRC-000037 pp.53–54)]
6. **Branch routing.** LAN interfaces and static routes with **Global** scope (only global prefixes are advertised and routed by the fabric); default gateway on MPLS port avoids static/BGP to the CE; classic BGP peers only at branches; L3 Direct Private WAN Forwarding and L3 LAN Forwarding enabled. [VERIFIED — 10-design/02 (SRC-000037 pp.57–68); 02-network/08]
7. **Segmentation.** Corporate stays in the Global VRF. **IoT** gets a custom VRF (true isolation, VRF ID carried in the fabric, route leaking off by default) through a VRF profile bound to all sites including the DCs (the hub must be a member of the VRF for end-to-end reach — internal 6.3.1 statement). **Guest** follows the official pattern: network context "Guest" + GUEST security zone + Local-scope interface (same subnet everywhere) + a path set sending guest traffic Direct to the Internet; a context alone does not isolate. [VERIFIED for VRF model, context semantics and guest pattern — 02-network/09 (SRC-000029 pp.433–437), 10-design/01 (SRC-000038 pp.34–36), 10-design/03 (SRC-000045 pp.34–42); UNVERIFIED (internal) for "hub must be in all VRFs" and for standard-VPN-from-custom-VRF limits — 02-network/09 playbook]
8. **Prisma Access.** Same TSG; Aggregate Bandwidth ≥ 50 Mbps per compute location; SASE Connectivity: local AS (default 65024, ≠ Prisma Access AS), tunnel inner pool (default 172.16.0.0/22 = 1,024 /31s; 40 sites × ≤4 circuits = ≤160 tunnels, fine), deployment mode **Internet-Only** (routes stay out of the Prisma Access backbone; private access is over the fabric), zone PUBLIC bound to the auto-created tunnels. Two Internet circuits → two tunnels with ECMP (session-level). ≤250 tunnels per RN-SPN. Enterprise prefixes: remove 192.168.0.0/16 if the Prisma Access infrastructure subnet is 192.168.255.0/24. [VERIFIED — 04-security/06 (SRC-000029 pp.663–680), 10-design/01 (SRC-000038 pp.54–55, 63–68), 10-design/02 (SRC-000037 pp.22–28)]
9. **Path policy.** Advanced stacks; MPLS+INET set: default rule = Standard VPN Any Public active (groups "Prisma Access: All Regions" / "Backup Regions"), backup Direct Any Public **or** VPN to DC if inspection is mandatory (design choice, see §4), L3 failure VPN on LTE; enterprise-default = VPN any private + any public active, groups Primary-DC/Secondary-DC for transit; control-app rule above both (paloalto-prisma-sdwan-base, all paths). [VERIFIED for the official DIA set — 10-design/02 (SRC-000037 pp.83–85); UNVERIFIED (internal) for the control-app rule — 03-application-traffic/02 WS-001]
10. **Security.** Zones PRIVATE/IOT/GUEST/PUBLIC/PRIVATEWAN/VPN bound per device (service_link entries "Auto created and managed by SDWAN" → PUBLIC); stack ≤4 sets + default; explicit allow rules per zone pair; rules bound to branches only. [VERIFIED — 04-security/01; 10-design/02 §6]

## 4. Answer (packet paths and failovers)

- **Branch → DC application.** First packet identified (port-based first match, then L7/SNI) → enterprise prefix → enterprise-default rule → candidates = fabric VPNs over MPLS and Internet to the DC with a route for the destination (DC site prefixes are programmed per link) → pruned by link status, LQM thresholds, app reachability, affinity → most available bandwidth → ESP over UDP 4500 to the active DC ION → decrypted, forwarded to the core via the core-peer-attracted route; the return is symmetric because only the branch's active DC ION advertises that branch prefix and DC IONs enforce routing symmetry. [VERIFIED for identification, rule flow, programmed routes, symmetry statement — 03-application-traffic/01–02, 10-design/01 (SRC-000038 p.43), 10-design/02 (SRC-000037 p.69); CORROBORATED for the evaluation order; UNVERIFIED (internal) for "only the active DC ION advertises"]
- **Branch → SaaS.** Non-enterprise destination → default rule → Standard VPN to the nearest Prisma Access location over any Internet circuit (ECMP by session), source-NAT at Prisma Access, security policy there; ZBFW rule PRIVATE→PUBLIC must allow the applications because the tunnel interfaces sit in PUBLIC. [VERIFIED — 10-design/02 §5.7, §6]
- **Branch → branch.** enterprise-default with Primary-DC group → transit through the regional DC ION, forwarded VPN-to-VPN inside the DC ION (unless "Force VPN to VPN Traffic to Local Next Hop" is set); MPLS-connected branches may also use the direct MPLS underlay if the set keeps Direct Any Private (default behaviour); add explicit branch-to-branch fabric links only for heavy pairs. [VERIFIED — 10-design/02 (SRC-000037 pp.70, 76–79), 10-design/01 (SRC-000038 p.54)]
- **(a) MPLS degrades.** Fabric VPN over MPLS stays up (keep-alive 1 s × 3) but LQM shows latency/loss/jitter above the SLA (built-in: All Apps 500 ms / 5 % / 100 ms; Media 150 ms / 2 % / 40 ms, or the custom SLA). Flows governed by a performance rule with Move Flows (graceful or forced) move to another in-policy **active** path (Internet VPN), else to an in-policy backup; apps with only "Create Incident" stay and raise `APPLICATION_PERFORMANCE_DEGRADED`/`CIRCUIT_PERFORMANCE_DEGRADED`. Backup paths are also used on LQM breach (this is not legacy active/standby). Fail-back to the active path when it is in policy again (5.2.1+ default). [VERIFIED — 10-design/01 (SRC-000038 pp.45–46), 03-application-traffic/02, 03-application-traffic/06; UNVERIFIED (internal) for LQM sampling cadence]
- **(b) DC ION fails.** Core routers lose the BGP session within the 3-second hold time and withdraw that ION's branch prefixes; branches detect the dead tunnels in ~3 s (keep-alive) and continue on their existing tunnels to the surviving DC ION, which becomes their active DC ION and advertises their prefixes; no branch configuration change. Requires the capacity rule (one ION carries all branches) and the default/summary route to core. Also: if a DC ION's core peer goes down while the ION is alive, all its fabric links are marked unusable so branches move the same way. [VERIFIED — 10-design/01 (SRC-000038 pp.40–41, 52), 02-network/08; UNVERIFIED (internal) for the exact re-homing time (KG-078)]
- **(c) Prisma Access tunnel drops.** Endpoint liveliness (ICMP every 10 s, 3 misses ≈ 30 s) marks that region endpoint down; with two ECMP tunnels the sessions rebalance to the remaining tunnel; if all Prisma Access endpoints are down the rule's backup path is used — Direct Any Public (uninspected DIA) in the official blueprint, or VPN to the DC security stack if the design requires inspection always (then the default rule backup = Prisma SD-WAN VPN Any Public/Private with Primary-DC group). Prisma Access itself detects a dead tunnel in ~50 s (IKEv2 liveness 5 s × 10) and BGP hold 30 s if tuned. [VERIFIED — 04-security/06 (SRC-000029 pp.676–680), 10-design/01 (SRC-000038 pp.66–67), 10-design/02 §5.2/§5.7]
